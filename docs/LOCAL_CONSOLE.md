# ローカル送信画面（7段階セットアップ）

[English](LOCAL_CONSOLE_EN.md) | 日本語

送信画面はCloud Runではなく、あなたのパソコンで動く小さな配信helperが `http://localhost:8765/console` に出します。画面を開く・再読み込みする・言語を切り替える・固定の指示文を表示/コピーするだけでは、Cloud Run・送信API・Firebaseへ一切通信しません。通信は画面のボタンを押した時だけで、Firebaseの認証ライブラリも手順1の「Appleでログイン」を押した時に初めて読み込みます。

## 必要なもの

- Node.js 22（`>=22.2.0 <23`。実測は22.23.4。[INSTALL](INSTALL.md)の版の条件と同じ）と、このリポジトリのbuild済みsource（`npm ci --ignore-scripts --no-audit --no-fund` と `npm run build`）。新しい依存はありません。
- 配置済みのAPI/MCPサービスのhttps originと、Firebase Webアプリの公開設定（`apiKey`・`authDomain`・`projectId`）。いずれも秘密ではなくブラウザに渡る値ですが、設定fileはcommitしません（`console.local.json` と `*.local.json` は `.gitignore` 済み）。
- Firebase Authenticationのauthorized domainsに `localhost` が入っていること（Appleログインのpopupに必要）。

## 設定fileと起動

`console.config.example.json` をコピーして `console.local.json` を作り、値を自分のものに置き換えます。keyはこの3つだけで、未知のkey・http origin・IPアドレス・path付きoriginは起動時に拒否します。

```json
{
  "apiOrigin": "https://sendtexttodotsapi-<PROJECT_NUMBER>.<REGION>.run.app",
  "mcpOrigin": "https://<MCP_SERVICE>-<PROJECT_NUMBER>.<REGION>.run.app",
  "firebase": { "apiKey": "...", "authDomain": "<project>.firebaseapp.com", "projectId": "<project>" }
}
```

```sh
npm run build
npm run console -- --config console.local.json          # 既定 http://localhost:8765/console
npm run console -- --config console.local.json --port 9000
```

helperは `127.0.0.1` だけで待ち受け、`Host: localhost:<port>` と完全に一致する要求だけを受けます。LAN公開・`0.0.0.0`・`file://` での直開きには対応しません。止めるときは Ctrl+C です。

## 画面でできること（7段階）

7つの手順は常に順に表示され、初めは手順1だけが有効で、2〜7は灰色です。完了した手順は薄く表示され、その枠のどこかをクリック（またはEnter/Space）すると見直しのために再び有効になります（見直すだけでは記録は消えません）。有効でない枠の中のボタンや入力欄は押せません。セットアップ（手順1〜6）を終えると、画面の一番下に完了の文面が表示され、手順7で送信を続けても表示されたままです（手順7の送信結果は完了の条件ではありません）。この画面とhelperは、進捗・入力した本文・ID tokenをメモリだけで扱い、cookie・localStorage・fileなどへ追加保存しません（再読み込みで初期化されます）。画面自身が残すのは表示用cookie `sttd_language`（言語の選択）だけです。これとは別に、Firebase SDK自身はログイン状態の復元のために既定の方法で認証sessionをブラウザ内に保存します。この保存はFirebaseの仕様で、本画面は変更していません。別のタブでログアウトや別アカウントへの切替があった場合も手順2〜7は戻り、再ログインを案内します。

1. **ログイン** — 「Appleでログイン」を押すと認証ライブラリを読み込み、入力元アプリと同じAppleアカウントでログインします。popupは押した時だけ開きます（ブロックされた場合はもう一度押してください）。別アカウントでやり直すと手順2〜7は戻ります。
2. **プラグインの追加と接続許可の確認** — プラグインを追加して接続を許可したら、「接続を確認」を1回押します（自動の再確認はありません）。接続が許可済み（「接続許可済み・受信開始待ち」または「受信中」）で利用も許可されていれば、自動で手順3へ進みます（受信中でも手順4は省略しません）。未接続・期限切れ・送信先変更の確認待ち・確認できない場合は進まず、次にすることを英日で案内します。送信先変更の確認待ち（別の受信先の設定が残っている）は、プラグインの接続をAppleでやり直し、最後の許可画面で以前の受信先設定の削除を確認すると解消します（コードでの接続では削除しません。削除は新しい配送の宛先を止めるもので、既に始まった配送を取り消すものではありません）。確認中は手順3〜7を一時的に封鎖し、接続の許可が続いていれば進捗は保持、そうでなければ手順3〜7を戻します。ここで「接続を解除」もできます。 利用許可（運営者の明示登録）も同時に表示し、許可されていない・確認できない・サービスが旧版で更新が必要、の3つを区別して案内します。いずれの場合も新しい送信へは進めませんが、接続解除と、前の送信の結果確認・中止はできます。 手順2には「プラグインを追加・接続する」の短い案内と展開できる手順があり、未接続でも接続済みでも見直せます（接続済みなら追加し直す必要はありません）。登録先として、helperの設定`mcpOrigin`の後ろに`/mcp`を付けたこの配置のServer URLを表示します（設定が無い時はURLを推定せず案内だけ）。このローカル画面（localhost）やAPIのoriginは登録しません。手順: ChatGPTのPlugins →「+」→「Add custom MCP server」で、分かる名前とServer URLを入れ、接続はHTTPS・認証はOAuthを選ぶ → 接続先・認証・警告を確認して作成・インストールし、手順1と同じAppleアカウントで同意する → この画面へ戻り「接続を確認」を押す（受信の開始は手順3で行います）。メニュー名や利用できるかどうかはChatGPTのアカウント・workspaceにより、変わることがあるため、画面の公式リンク（[Connect and test your plugin](https://developers.openai.com/plugins/deploy/connect-chatgpt)・[Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server)）も確認してください。ガイドを開く・リンクを押す・言語を切り替える操作では、この画面は通信しません。
3. **テスト用Dotsプロンプト（受信開始）** — [Dotsガイド](DOTS_GUIDE.md)のテスト用文面を表示/コピーし、受信するDotsへ貼り付け、同じ会話で追加したプラグインを選んで「このDotsで受信を開始」と依頼してから「Dotsへ貼り付けて次へ」を押すと、手順4へ進みます。コピーできないブラウザでは手動コピーを確認してから進めます。コピーしてもDotsへは送られません。
4. **受信状態の確認** — 受信開始を依頼した後、「受信状態を確認」を1回押します。受信中で利用も許可されている場合だけ手順5へ進みます。受信開始待ちならこの手順に留まり、確認できない結果を成功とは扱いません。
5. **固定文の送信テスト** — 編集欄はなく、固定文（日本語「SendTextToDotsの送信テストです。」、英語「This is a SendTextToDots delivery test.」）を表示します。送る本文は画面の入力値ではなくこの固定文です。「固定文を送信」を押し（1回のPOST。二重クリックで2件にはなりません）、Dotsで受信した本文が固定文と一致することを自分で確認してから「Dotsで本文一致を確認して次へ」を押します。「受領」はcallbackの2xxで、一致の証明ではありません。未送信・失敗・中止・期限切れでは進めず、結果不明の場合は実際にDotsで一致を確認したうえで進めます（画面は不明を成功へ書き換えません）。
6. **運用用Dotsプロンプト** — 運用用の文面を表示/コピーして同じDotsへ貼り付け、「Dotsへ貼り付けて完了」を押すと、セットアップの完了文面が表示され、手順7が開きます（手順7へscrollします）。これはあなたの確認操作による進捗で、サーバーがDotsへの適用を検証したわけではありません。

7. **自由な文章を送信** — 手順6の完了後に開く入力欄へ本文を入力し、「送信」を押します。次の本文は「新しい送信」から入力します。空白だけの本文や4096 UTF-8 byteを超える本文は送信前に拒否します。固定テストの一致確認とは別に送信結果を扱い、自由送信の成否はセットアップ完了の条件にしません。

完了後は手順7で通常の送信を繰り返せます（手順3/6の再コピーは不要です）。再ログイン・方式の切替・接続や利用許可の喪失・受信中でない状態・テスト用文面の再適用があると、それに依存する手順は戻ります（テスト用文面の再適用では手順4の受信確認からやり直し、手順7も封鎖されます）。

**手順の省略（右上の「スキップ」）** — 手順1・2・3・5・6・7の見出しの右上に灰色の「スキップ」があり、手順4は「必須」で省略できません。省略は「完了」とは別に記録し、未確認の手順を完了・本文一致・貼付済みとは扱いません。手順1の「スキップ（保存済みのログインで再開）」は、押した時だけ認証ライブラリを読み込み、このブラウザにFirebaseが保存している、選んだ方式のログインを確認します。ID tokenを更新し、この配置のproject・tenantなし・ログイン方法（Appleか、コードなら専用UIDとコードの印）が合う時だけ手順2へ進みます。保存が無い・期限切れ・別の配置・方式が違う場合は手順1に留まり、通常のログインを案内します（popup・ログアウト・コード発行はしません）。復元したコードログインでは、この画面が発行したコードでない限り、再発行・取消・コード確認は表示しません。手順2・3を省略しても、手順4の明示確認（受信中かつ利用許可）までは送信できません。手順5・6を省略すると完了の文面は「未確認の手順があります」になり、戻って実施できます。手順7の「スキップ」は何も送らずに今回の案内を終えるだけで、結果が確定していない送信がある間は使えません。再ログイン・方式の切替・接続や受信の喪失などでは、省略も含めて関係する手順が戻ります。

## ログインsessionとtoken更新

認証が必要なボタン操作では、helperで中継する前に`user.getIdToken()`で有効なFirebase ID tokenを取得します。SDKは既存のログインsessionから短期tokenを更新できるため、寿命が約1時間でも、毎時間の手動ログインが必要という意味ではありません。サインアウト・sessionの失効や無効化があれば、再ログインが必要になることはあります。画面のメモリ上のセットアップ進捗とFirebaseのブラウザsessionは別です。背景での状態監視や送信を追加するものではありません。[sessionと自動送信の説明](API.md#firebase-sessions)も参照してください。

## helperが中継するもの

helperは、画面のボタン操作に対応する次の要求だけを、設定した固定originへ中継します。ブラウザから本番originへ直接通信せず、Cloud Run側のCORS・権限は変えていません。

| 画面からの要求 | 上流 |
| --- | --- |
| `GET /v1/web/connection`・`POST /v1/web/disconnect` | `mcpOrigin` |
| `POST /v2/commands`・`GET /v2/commands/{id}`・`POST /v2/commands/{id}/cancel` | `apiOrigin` |

要求ごとに `Authorization: Bearer <Firebase ID token>` と、起動時に作る乱数（local nonce）を必須にし、Hostの不一致・Originの不一致・nonceの欠落や重複・許可外のpath/method・本文超過（送信のJSON全体で32 KiB。本文の上限4096 byteはAPI側のまま）は上流を呼ぶ前に拒否します。上流の応答は64 KiBまで読み、超える場合は打ち切って固定のエラーにします。上流へ転送するheaderは `Authorization`（送信時は `Content-Type` と `Idempotency-Key` も）だけで、Cookie・Origin・Forwarded・nonceは送りません。応答は状態・本文・`Content-Type`・`Retry-After` だけを返し、`Set-Cookie` は転送しません。token・本文・秘密は保存もログ出力もしません。任意URLへの中継・redirectの追従はできません。

helperが上流を呼ぶ前に自分で拒否した応答（古い画面のnonce不一致・許可外のpath/method・本文超過など）には固定header `X-Sttd-Local-Refusal: 1` を付け、画面はこれがある時だけ「送信されていない」と表示して再読み込みを案内します（本文一致の確認へは進めません）。上流の応答の同名headerは転送しないため、上流のエラーを未送信に見せかけることはできません。上流を呼んだ後の失敗（502など）は従来どおり結果不明です。結果が確定していない送信がある時に再ログイン・認証の喪失・状態の再確認・テスト用文面の再適用で手順が戻った場合は、重複して届く可能性の注意を表示したままにします（自動の照会・取消・再送はしません）。

## 制約

- 第三者の環境・実ブラウザでの動作は合成試験以外で未確認です（[LIMITATIONS](LIMITATIONS.md)）。
- helperはあなたのパソコンで動く開発補助で、認証や秘密を追加で扱いません。Cloud側の設定・サービスの起動停止は行いません。
- この画面の送信は平文の`POST /v2/commands`だけです。暗号化した本文の送信・公開鍵の取得・鍵の再発行の画面はありません。これらは別の[API](API.md#encryption-key)で、入力元の端末側のclientが暗号化し、SendTextToDotsが復号して配送します（E2E暗号化ではありません）。
- Ctrl+Cでhelperを止めても、止まるのはこのパソコンの画面だけです。Cloudのサービスは動き続け、Dotsの購読も残ります。認可と購読を失効させるには手順2の「接続を解除」を使います。Cloudのサービスの停止は導入者の操作です。

## 開発者向け6桁コードで接続する（operator mode）

通常の`npm run console`は従来どおりAppleでログインする配信modeで、コード発行の操作口はありません（ステップ1に「この配置ではコード発行が設定されていません」と表示）。配置設定で`developerLogin: 'operator-code-v1'`にした配置で、自分の配置へ管理権限を持つ端末だけが、明示的にoperator modeを起動します。

```
node dist/console/operator-server.js --config console.local.json --operator operator.local.json
```

`operator.local.json`には署名用service accountの`signingServiceAccount`が必須です（[設定](CONFIGURATION.md)）。helperは既定のADCで動き、その資格にこのservice accountへの`iam.serviceAccounts.signBlob`が要ります。

1. ステップ1の「ログイン方法を選ぶ」で「コードでログイン」を選び、「続ける」を押します（選ぶだけでは発行・通信しません）。「Appleでログイン（推奨）」を選んで「続ける」を押すとAppleのログインを始めます。「続ける」は1つだけで、選んだ方式の説明と操作だけが表示されます。発行に成功すると手順2へ進み（追加方法が開きます）、6桁のコードと残り時間を表示します。発行しただけでは手順3以降は開きません。
2. 10分以内に、プラグインを追加した後の接続画面でコードを入力します。コードの使用は1回だけです。続けて通常の同意を行います（受信の開始は手順3、確認は手順4です）。
3. コンソールで「接続を確認」を押すと、同じ利用単位でコンソールもログインします。自動での確認（poll）はしません。
4. 「再発行」は現在のコードとそのコードによる接続を終了して作り直します。新しいコードを確保できなかったときは、現在のコードと接続は変わりません。

AppleとコードはStep 1で切り替えられます。切り替えても以前の接続は自動では止まりません。以前のプラグインを削除し、ステップ2から追加し直してください。以前の接続は新しい接続へ引き継がれません。

operatorの照会用secretはhelperのメモリだけにあり、helperを終了すると発行済みコードの照会・再発行はできません（未使用のコードは10分で失効します。新しく発行してください）。
